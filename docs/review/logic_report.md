## 2. Заказы покупателей

### LOG-01. Недостаточная проверка позиций заказа

**Файл:** `app/views/sales_order_view.py`  
**Методы:** `post()`, `put()`  
**Категория:** валидация данных  
**Приоритет:** высокий  
**Статус:** требует исправления.

Некорректные или отсутствующие `product_id`, а также UUID несуществующих товаров могут пропускаться без сообщения об ошибке. В результате заказ может сохраниться без части переданных позиций.

**Рекомендация:** проверять наличие идентификатора товара, его формат и существование соответствующей записи в базе данных. При обнаружении ошибки возвращать понятное сообщение и соответствующий HTTP-статус.

### LOG-02. Отсутствовало ограничение максимальной скидки

**Файлы:**
- `app/views/sales_order_view.py`;
- `app/models.py`;
- `database/schema.sql`.

**Методы:** `post()`, `put()`  
**Категория:** валидация данных и целостность БД  
**Приоритет:** высокий  
**Статус:** исправлено.

Изначально API и модель не ограничивали максимальную скидку. Значение больше 100% могло привести к отрицательной стоимости позиции.

В ходе ревью выполнены следующие исправления:

- добавлена проверка скидки в API;
- установлен допустимый диапазон от 0 до 100;
- добавлено ограничение `CheckConstraint` в модели;
- добавлено соответствующее ограничение в SQL-схеме;
- созданы автоматизированные тесты для проверки допустимых и недопустимых значений.

### LOG-03. Возможная ошибка при обновлении заказа без списка позиций

**Файл:** `app/views/sales_order_view.py`  
**Метод:** `put()`  
**Категория:** обработка ошибок  
**Приоритет:** высокий  
**Статус:** требует исправления.

Переменная `items_list` создаётся только при наличии поля `items`. Далее она используется при пересчёте связанного производственного заказа. Если поле `items` отсутствует, но связанный производственный заказ существует и автоматическое создание производства включено, возможно возникновение `UnboundLocalError`.

**Рекомендация:** заранее инициализировать переменную и отдельно обрабатывать ситуацию, когда поле `items` не передано в запросе.

### LOG-04. Возможна коллизия номеров заказов

**Файл:** `app/views/sales_order_view.py`  
**Метод:** `post()`  
**Категория:** целостность данных  
**Приоритет:** средний  
**Статус:** требует исправления.

Номер заказа формируется через поиск максимального номера и увеличение его на единицу. При одновременном создании заказов несколькими пользователями возможна генерация одинаковых номеров. Уникальное ограничение базы данных предотвратит сохранение дубликата, но один из запросов завершится ошибкой.

**Рекомендация:** использовать безопасный механизм генерации уникальных номеров, например последовательность базы данных или отдельный механизм нумерации с обработкой конфликтов.

### LOG-05. Раздельное сохранение заказа покупателя и производственного заказа

**Файл:** `app/views/sales_order_view.py`  
**Метод:** `post()`  
**Категория:** транзакционность  
**Приоритет:** высокий  
**Статус:** требует исправления.

Сначала выполняется сохранение заказа покупателя, затем отдельное сохранение производственного заказа. При ошибке второго этапа заказ покупателя может остаться в базе без связанного производственного заказа.

**Рекомендация:** объединить связанные операции в одну транзакцию, чтобы при ошибке все изменения отменялись.

### LOG-06. Возможная потеря информации о выполненных работах

**Файл:** `app/views/sales_order_view.py`  
**Метод:** `put()`  
**Категория:** сохранность данных  
**Приоритет:** высокий  
**Статус:** требует исправления.

При пересоздании позиций связанного производственного заказа старые позиции удаляются, а новые создаются с `completed_quantity=0`. Это может привести к потере ранее зафиксированного объёма выполненных работ.

**Рекомендация:** сохранять сведения о выполненных объёмах при обновлении позиций либо запрещать пересоздание позиций, если по ним уже ведётся производство.

## 3. Себестоимость и расчёты

### LOG-07. Использование нулевой стоимости при отсутствии цены

**Файлы:**
- `app/services/sales_order_service.py`;
- `app/services/production_order_service.py`.

**Категория:** бизнес-логика и расчёты  
**Приоритет:** высокий  
**Статус:** требует исправления.

Если цена материала или операции не найдена, сервис подставляет `0.0`. В результате себестоимость может быть занижена, а прибыль завышена. Пользователь не получает предупреждения об отсутствии цены.

**Рекомендация:** проверять наличие цены и уведомлять пользователя о недостающих данных. Не выполнять окончательный расчёт, если обязательная цена отсутствует.

### LOG-08. Не учитывается дата заказа при выборе цены

**Файлы:**
- `app/services/sales_order_service.py`;
- `app/services/production_order_service.py`.

**Категория:** корректность расчётов  
**Приоритет:** высокий  
**Статус:** требует исправления.

При выборе цены используется последняя запись по `effective_date` без ограничения датой заказа. Поэтому исторические заказы могут рассчитываться по цене, которая появилась позднее даты заказа.

**Рекомендация:** выбирать цену, действовавшую на дату создания соответствующего заказа.

### LOG-09. Возможная ошибка при отсутствии связанного товара

**Файл:** `app/services/sales_order_service.py`  
**Метод:** `calculate_cost()`  
**Категория:** обработка ошибок  
**Приоритет:** средний  
**Статус:** требует исправления.

В отличие от сервиса производственных заказов, здесь нет отдельной проверки наличия товара перед обращением к `product.spec_materials`. При отсутствии связанного товара возможно исключение.

**Рекомендация:** добавить проверку существования связанного товара и обработку ситуации, когда объект отсутствует.

## 4. Производственные заказы

### LOG-10. Не проверяется превышение выполненного количества

**Файлы:**
- `app/views/production_order_view.py`;
- `app/models.py`.

**Категория:** валидация и целостность данных  
**Приоритет:** высокий  
**Статус:** требует исправления.

В модели есть ограничение `completed_quantity >= 0`, но отсутствует ограничение `completed_quantity <= quantity`. API также не выполняет такую проверку при создании позиции.

**Рекомендация:** добавить проверку, запрещающую превышение выполненного количества над общим количеством позиции.

### LOG-11. Некорректные позиции могут пропускаться

**Файл:** `app/views/production_order_view.py`  
**Метод:** `post()`  
**Категория:** валидация данных  
**Приоритет:** средний  
**Статус:** требует исправления.

Если UUID товара имеет неверный формат, позиция пропускается через `continue`. Заказ при этом может быть сохранён без переданной позиции.

**Рекомендация:** возвращать ошибку валидации и не сохранять заказ с неполным набором переданных позиций.

### LOG-12. Отсутствует обновление состава производственного заказа

**Файл:** `app/views/production_order_view.py`  
**Метод:** `put()`  
**Категория:** функциональность API  
**Приоритет:** средний  
**Статус:** требует сверки с требованиями проекта.

Метод обновляет номер, дату, подразделение и статус, но не обрабатывает поле `items`. Если по требованиям проекта состав производственного заказа должен редактироваться через этот API, функциональность отсутствует.

**Рекомендация:** сверить поведение с требованиями проекта и при необходимости добавить обработку списка позиций.

### LOG-13. Недостаточная обработка ошибок даты

**Файлы:**
- `app/views/sales_order_view.py`;
- `app/views/production_order_view.py`.

**Категория:** обработка ошибок  
**Приоритет:** средний  
**Статус:** требует исправления.

Используется `date.fromisoformat()`. Некорректная дата может вызвать исключение. Явная обработка `ValueError` в соответствующих местах не обнаружена.

**Рекомендация:** проверять формат даты до сохранения данных и возвращать понятную ошибку при неверном значении.

## 5. Положительные результаты проверки

В ходе ревью также выявлены реализованные механизмы защиты данных:

- в моделях используются внешние ключи и ограничения целостности;
- количество позиций заказов должно быть больше нуля;
- цена позиции не может быть отрицательной;
- удаление используемого товара ограничено через `ondelete=RESTRICT`;
- статус производственного заказа ограничен допустимыми значениями;
- сервис производственных заказов отдельно обрабатывает отсутствие связанного товара;
- для скидки реализовано ограничение от 0 до 100 процентов.
