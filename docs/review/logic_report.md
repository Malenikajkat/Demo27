Отчёт по проверке логики приложения и базы данных

Этап: День 3 — проверка логики приложения, API, SQL и тестов.

1. Проверка маршрутов и обработчиков

В проекте используются Flask Blueprints и обработчики на основе классов "MethodView".

Проверены маршруты следующих разделов:

- авторизация;
- администрирование пользователей;
- клиенты;
- товары;
- материалы;
- операции;
- спецификации;
- заказы на производство;
- заказы покупателей;
- заметки.

Обнаружено, что для разных разделов используются методы GET, POST, PUT и DELETE. Для API заметок предусмотрены отдельные GET-маршруты получения списка и одной записи.

Проверена организация регистрации Blueprint в "app/__init__.py".

2. Проверка валидации и HTTP-статусов

В "app/views/note_view.py" проверяются параметры пагинации:

- "skip" не может быть отрицательным;
- "limit" должен быть больше нуля.

Для некорректных параметров возвращается HTTP 400.

При отсутствии заметки возвращается HTTP 404. При ошибке обработки запроса к базе данных предусмотрен HTTP 500 с откатом транзакции.

Проведена ручная проверка API через Tetiva:

| Запрос| Результат |
|---|---|
| GET "/api/notes/"| 200 OK |
GET "/api/notes/999999"| 404 Not Found
GET "/api/notes/?skip=-1"| 400 Bad Request
GET "/api/notes/?limit=0"| 400 Bad Request
GET "/api/notes/?skip=0&limit=10"| 200 OK

Все перечисленные запросы вернули ожидаемые статусы.

3. Проверка SQL-запросов

Проведен поиск SQL-запросов в Python-файлах и SQL-скриптах проекта.

Основная часть запросов реализована средствами SQLAlchemy ORM: используются "select()", "where()", "join()" и другие конструкции ORM.

Также обнаружены отдельные запросы через "sqlalchemy.text()" в:

- "app/views/production_order_view.py";
- "app/views/sales_order_view.py".

Проверенные запросы используют статический SQL без подстановки пользовательского ввода через форматирование строк.

По результатам просмотренных участков явных признаков SQL-инъекций не обнаружено.

5. Сравнение ER-диаграммы, schema.sql и моделей

При сравнении ER-диаграммы, "database/schema.sql" и "app/models.py" обнаружено расхождение.

В модели "ProductionOrder" из "app/models.py" присутствует поле "sales_order_id", связанное внешним ключом с "sales_orders.sales_order_id".

Однако в определении таблицы "production_orders" в "database/schema.sql" это поле и соответствующий внешний ключ отсутствуют.

Замечание: необходимо синхронизировать ORM-модель и SQL-схему, чтобы структура базы данных соответствовала структуре приложения и ER-диаграмме.

6. Проверка автоматических тестов

Проверены файлы:

- "tests/conftest.py";
- "tests/test_auth.py";
- "tests/test_notes.py".

Для тестирования используется SQLite в оперативной памяти. Это позволяет выполнять тесты без подключения к основной PostgreSQL-базе.

Выполнена команда:

"python -m pytest -v"

Результат:

14 passed in 8.42s

Проверено 14 тестов:

Авторизация — 7 тестов:

- успешная авторизация;
- неправильный пароль;
- несуществующий пользователь;
- блокировка после неверных попыток;
- отсутствие обязательных полей;
- получение данных пользователя без авторизации;
- получение данных пользователя после авторизации.

API заметок — 7 тестов:

- получение списка заметок;
- проверка структуры ответа;
- получение пустого списка;
- проверка некорректных параметров;
- проверка JSON-формата;
- получение заметки по ID;
- обработка отсутствующей заметки.

Все 14 тестов завершились успешно.

При этом автоматические тесты охватывают авторизацию и API заметок, но не все остальные разделы приложения.
