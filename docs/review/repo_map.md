# Карта структуры проекта Demo27

**Проект:** Demo27  
**Тип приложения:** веб-приложение на Flask  
**База данных:** PostgreSQL  
**Основные технологии:** Python, Flask, SQLAlchemy, HTML, CSS, SQL

## 1. Корневая структура

| Каталог / файл | Назначение |
|---|---|
| `app/` | Основной программный код приложения |
| `database/` | SQL-схема и запросы базы данных |
| `docs/review/` | Документы, созданные в ходе ревьюирования |
| `image/` | Изображения проекта |
| `tests/` | Автоматизированные тесты |
| `web/` | HTML-страницы и CSS-стили |
| `requirements.txt` | Зависимости Python |
| `run.py` | Точка запуска приложения |
| `.gitignore` | Исключения Git |

## 2. Структура приложения app/

### 2.1. Основные файлы

| Файл | Назначение |
|---|---|
| `__init__.py` | Создание и настройка Flask-приложения |
| `auth.py` | Функции, связанные с авторизацией |
| `config.py` | Конфигурация приложения |

### 2.2. Blueprints — маршруты приложения

Каталог `app/blueprints/` содержит модули маршрутизации:

- `admin.py` — маршруты администратора;
- `auth.py` — регистрация и авторизация;
- `clients.py` — работа с клиентами;
- `materials.py` — работа с материалами;
- `notes.py` — работа с заметками;
- `operations.py` — работа с операциями;
- `production_orders.py` — производственные заказы;
- `products.py` — работа с продукцией;
- `puzzle_captcha.py` — маршруты CAPTCHA;
- `sales_orders.py` — заказы продаж;
- `specifications.py` — спецификации;
- `web.py` — веб-страницы приложения.

### 2.3. DTO — объекты передачи данных

Каталог `app/dtos/` содержит модули преобразования и передачи данных между частями приложения.

В нём находятся DTO для клиентов, материалов, заметок, операций, продукции, производственных заказов, заказов продаж, спецификаций и пользователей.

### 2.4. Repositories — слой доступа к данным

Каталог `app/repositories/` содержит базовый репозиторий и специализированные репозитории для работы с клиентами, материалами, операциями, продукцией, производственными заказами, заказами продаж, спецификациями и пользователями.

### 2.5. Services — бизнес-логика

Каталог `app/services/` содержит базовый сервис и сервисы для авторизации, клиентов, материалов, операций, продукции, производственных заказов, заказов продаж, спецификаций и пользователей.

### 2.6. Views — представления и обработка запросов

Каталог `app/views/` содержит базовое представление и специализированные модули для администратора, клиентов, материалов, заметок, операций, продукции, производственных заказов, заказов продаж и спецификаций.

## 7. Общая архитектура

По структуре каталогов проект разделён на несколько логических уровней:

1. **Blueprints** — маршрутизация и обработка входящих запросов.
2. **Views** — представления и обработка операций приложения.
3. **Services** — бизнес-логика.
4. **Repositories** — взаимодействие с данными.
5. **DTOs** — передача данных между компонентами.
6. **Models** — описание моделей базы данных.
7. **Web** — пользовательский интерфейс.
8. **Tests** — автоматизированная проверка отдельных функций.

Такое разделение помогает распределять ответственность между компонентами, упрощает сопровождение и позволяет проверять отдельные части приложения.

## 8. Запуск проекта и дополнительные замечания

### 8.1. Запуск приложения

1. Активировать виртуальное окружение.
2. Установить зависимости командой `pip install -r requirements.txt`.
3. Проверить настройки подключения к базе данных и переменные окружения в `.env`.
4. Запустить приложение командой `python run.py`.
5. При успешном запуске приложение доступно по адресу `http://127.0.0.1:5000`.

Точка входа — `run.py`. В нём вызывается фабрика приложения `create_app()`. Сервер запускается на порту 5000 с включённым режимом отладки.

### 8.2. Отсутствующие материалы

При проверке структуры репозитория не обнаружены:

- каталог `scripts/`;
- коллекция запросов Postman;
- файл `er_diagram.pdf`;
- файл `README.md`.

Из-за отсутствия этих материалов проверить соответствующие инструкции, коллекцию запросов и соответствие схемы базы данных ER-диаграмме по указанным файлам невозможно. Это следует учитывать при оценке полноты документации проекта.
