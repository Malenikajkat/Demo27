# Отчёт по ревью безопасности, зависимостей, фронтенда и документации

## Ревью безопасности: хранение секретов и паролей, контроль доступа, XSS/CSRF-риски в web-шаблонах

### Отсутствие контроля доступа на CRUD-эндпоинтах справочников

Ни один из CRUD-эндпоинтов справочников (clients, products, materials, operations, specifications, orders) не защищён @login_required и не проверяет роль пользователя. Любой неавторизованный клиент может создавать, изменять и удалять клиентов, продукцию, материалы и заказы. Защита присутствует только в admin_view.py и частично в notes_bp.

**Рекомендация**: добавить @login_required на все state-changing маршруты и проверку роли (current_user.role) для операций, требующих повышенных привилегий.

### Регистрация с произвольной ролью

POST /api/auth/register принимает role из тела запроса:
python

role = data.get("role", "Пользователь")

Любой аноним может зарегистрироваться как "Администратор" и получить полный доступ к /api/admin/users/. В докстринге это честно описано как «потенциальная уязвимость», но код всё равно так делает.

**Рекомендация**: убрать role из публичного register (всегда "Пользователь"), либо требовать @login_required + current_user.role == "Администратор" для регистрации с явной ролью.

### Блокировка проверяется после проверки пароля

Файлы: app/blueprints/auth.py, app/blueprints/web.py

В обработчиках входа проверка is_blocked выполняется после проверки корректности пароля. Это позволяет перебирать пароли до бесконечности и подобрать верный. Если администратор разблокирует пользователя, не поменяв пароль, аккаунт будет скомпрометирован.

**Рекомендация**: сначала проверять user.is_blocked (→ 403), затем проверять пароль.

### XSS

Приложение построено на паттерне «Jinja-шаблон + клиентский JS, который собирает HTML через innerHTML и шаблонные строки из данных API». Это создаёт множественные точки XSS.

Пример — admin-dashboard.html, editUser через inline-атрибут:
js

onclick='editUser(${user.user_id}, \'${user.login}\', \'${user.role}\')'

Если login содержит ' или </script>, происходит инъекция в атрибут/разметку. user.login приходит из API — это пользовательские данные.

**Рекомендация**: не собирать HTML через innerHTML с интерполяцией пользовательских данных; использовать textContent, createElement или экранирование; для inline-обработчиков — addEventListener вместо onclick с интерполяцией.

### CSRF-защиты нет

В requirements.txt нет Flask-WTF / Flask-SeaSurf. Все state-changing маршруты (POST /api/clients/, POST /api/sales-orders/, DELETE /api/clients/<id>, POST /logout) принимают запросы без CSRF-токена.

**Рекомендация**: подключить Flask-WTF (CSRFProtect) или Flask-SeaSurf, включить защиту для всех POST/PUT/PATCH/DELETE и передавать токен в шаблоны/заголовки.

## Ревью фронтенд-части web: валидность HTML, согласованность стилей, тексты интерфейса

### Дублирование CSS в шаблонах

production-orders.html содержит style с .status-badge, .status-new и т.д.,
а sales-orders.html — .order-total-bar. При этом базовые .modal-body, .modal-body table тоже переопределяются локально.
Это разъезжается с base-dashboard.html.

**Рекомендация**: вынести общие стили (статусы, таблицы в модалках) в styles.css или в base-dashboard.html.

### Иконки — эмодзи

Иконки реализованы эмодзи (✏️ 💰 🗑️ 👁️). Работает, но не консистентно с остальным UI; для продакшна лучше SVG или иконочный шрифт.
