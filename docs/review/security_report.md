## 2. Что сделано корректно

- Пароли в Python-коде хешируются через `werkzeug.security.generate_password_hash`, а проверяются через `check_password_hash`.
- В коде нет явного сохранения введённого пароля в открытом виде.
- В SQL-поиске по исходникам не обнаружена очевидная конкатенация пользовательских значений в SQL-строки.
- Для административных операций в `app/views/admin_view.py` предусмотрена проверка роли администратора.

## 3. Дополнительные замечания

- `database/schema.sql:283-287` содержит демонстрационные записи пользователей с placeholder-значением `dummyhash`; такие записи не являются корректными хешами паролей.
- В `app/models.py` есть поле `blocked_until`, но механизм блокировки фактически опирается на `is_blocked` и `failed_attempts`; временная блокировка не реализована.
- В `app/blueprints/puzzle_captcha.py` описан отдельный API капчи, но текущая фабрика приложения его не регистрирует.
- Защитные HTTP-заголовки (CSP, HSTS для HTTPS, `X-Content-Type-Options`, `Referrer-Policy`) явно не задаются.

## 4. Вывод

Наиболее опасные риски — повышение привилегий через регистрацию, доступ к API без авторизации, утечка заметок между пользователями, stored XSS и известные секреты по умолчанию. Перед публикацией приложения необходимы исправления контроля доступа и конфигурации, устранение небезопасной вставки HTML, CSRF-защита и полноценный динамический тест безопасности.
