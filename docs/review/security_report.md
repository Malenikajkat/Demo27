В ходе четвёртого этапа проверены конфигурация Flask, механизмы авторизации и регистрации, контроль доступа, обработка пользовательских данных, HTML-шаблоны, CSS, документация и структура проекта.

2. Проверка безопасности

2.1. Хранение паролей

Положительные моменты:

- Для хеширования паролей используется "generate_password_hash()" из Werkzeug.
- Для проверки паролей используется "check_password_hash()".
- Пароли не возвращаются в ответах проверенного API авторизации.

Недостатки:

- В проверенных функциях регистрации не обнаружена полноценная проверка сложности и минимальной длины пароля.
- В конфигурации присутствует значение пароля базы данных по умолчанию "12345".

Рекомендации:

- Добавить серверную проверку длины и допустимого формата пароля.
- Не использовать пароль базы данных по умолчанию в production.
- Хранить реальные секреты только в переменных окружения.

2.2. Секретный ключ и конфигурация

В "app/config.py" обнаружено значение "SECRET_KEY" по умолчанию:

"production-is-system-secret-key-change-me"

Использование известного значения в production небезопасно. Если переменная окружения не задана, приложение может использовать это значение.

Также в функции формирования адреса базы данных предусмотрен пароль по умолчанию "12345".

В "run.py" используется "debug=True". Если файл применяется для запуска production-приложения, режим отладки необходимо отключить.

Рекомендации:

- Требовать отдельный случайный "SECRET_KEY" для production-конфигурации.
- Не задавать пароль базы данных по умолчанию.
- Отключить режим отладки при production-запуске.
- Разделить настройки разработки, тестирования и production.

2.3. Контроль доступа

Положительные моменты:

- Административные маршруты используют "login_required".
- Дополнительно проверяется роль администратора.
- В проверенном административном маршруте предусмотрено ограничение на удаление собственной учётной записи.

Критическое замечание:

В обработчике регистрации "app/blueprints/auth.py" роль пользователя берётся непосредственно из JSON:

"role = data.get("role", "Пользователь")"

В самом обработчике не обнаружена проверка полномочий на создание администратора.

Если регистрационный маршрут доступен без авторизации и принимает переданную роль, пользователь может попытаться зарегистрироваться с ролью администратора.

Рекомендация: публичная регистрация должна всегда назначать роль «Пользователь». Создание администратора должно выполняться только через защищённый административный механизм.

2.4. XSS и обработка пользовательских данных

В проверенных HTML-файлах обнаружены места, где значения, полученные из API, вставляются в HTML через "innerHTML".

Проблемные участки обнаружены, в частности, в:

- "web/admin-dashboard.html";
- "web/clients.html";
- "web/materials.html";
- "web/specifications.html";
- "web/sales-orders.html";
- "web/user-dashboard.html";
- "web/notes.html".

Вставка названий, имён пользователей, заметок, уведомлений и других значений без безопасного экранирования может создавать риск межсайтового скриптинга (XSS), если данные содержат вредоносную HTML-разметку или JavaScript.

Отдельного внимания требуют значения, передаваемые в HTML через "innerHTML" и встроенные обработчики событий.

Рекомендации:

- Использовать "textContent" для вывода обычного текста.
- Не вставлять непроверенные значения API непосредственно через "innerHTML".
- Для создания элементов интерфейса применять "createElement" и "addEventListener".
- Если вставка HTML необходима, использовать безопасное экранирование.
- Проверять и ограничивать входные данные на стороне сервера.

2.5. CSRF и сессии

В проверенных расширениях и конфигурации приложения не обнаружена инициализация CSRF-защиты.

При этом приложение использует сессии Flask-Login и содержит операции, изменяющие данные посредством POST, PUT и DELETE.

В проверенных формах


и запросах не обнаружены явные CSRF-токены.

Рекомендации:

- Рассмотреть подключение Flask-WTF "CSRFProtect".
- Добавить CSRF-токены для операций, изменяющих данные.
- Настроить параметры cookie: "Secure", "HttpOnly", "SameSite".
- Проверить настройки CORS и поведение сессионных cookie.

Отсутствие обнаруженной защиты в проверенных файлах требует дополнительной проверки всех способов отправки запросов.

2.6. Авторизация и дополнительные замечания

- В "app/blueprints/web.py" значение "captcha_ok" устанавливается в "True". Следовательно, серверная проверка решения CAPTCHA в рассмотренном обработчике фактически не выполняется.
- Ограничение количества попыток входа реализовано на уровне учётной записи. Отдельное ограничение по IP-адресу в проверенном коде не обнаружено.
- В "app/__init__.py" вызывается "db.create_all()" при создании приложения. Для управления изменениями структуры БД рекомендуется использовать миграции.
- В "app/__init__.py" результат проверки подключения к БД не препятствует запуску приложения при ошибке подключения.
- В ".gitignore" исключены каталоги "migrations/" и "alembic/". Следует проверить, не мешает ли это хранению и передаче файлов миграций через Git.

3. Проверка HTML и CSS

3.1. HTML и JavaScript

Проверены HTML-страницы проекта, включая панели администратора и пользователя, страницы клиентов, материалов, спецификаций, заказов, заметок, товаров и операций, а также страницу авторизации.

Обнаруженные замечания:

"web/specifications.html":

- В таблице с пятью столбцами в отдельных состояниях используется "colspan="6"".
- Загрузка связанных списков выполняется без ожидания завершения, что может приводить к отсутствию данных при открытии модального окна.
- Преобразование числовых значений через "parseFloat(...) || 1.0" может подменять нулевое или некорректное значение единицей.
- Обнаружены потенциально небезопасные вставки данных через "innerHTML".

"web/sales-orders.html":

- В функции "viewOrder()" используется неопределённая переменная "prodItem".
- Используется ID "viewProdOrderModalBody", не соответствующий ID элемента в разметке.
- Обнаружена несогласованность логики отображения заказов.
- Некоторые поля формы не имеют полноценной HTML-валидации.
- Флаг "isViewingSalesOrder" может не сбрасываться после просмотра заказа.
- Обнаружены вставки значений API через "innerHTML".

"web/production-orders.html":

- Обнаружена проблема с вложенностью элементов формы ".form-group".
- Необходимо привести структуру HTML формы к корректной иерархии.
- Следует проверить корректность отображения формы и её поведения при редактировании и просмотре заказа.

"web/materials.html":

- Обнаружены потенциально небезопасные вставки данных через "innerHTML".
- В разметке присутствуют повторяющиеся значения "id="modalTitle"".
- В отдельных состояниях таблицы количество столбцов не совпадает с указанным "colspan".
- Числовые значения цены требуют более строгой проверки.

"web/clients.html":

- Значения клиентов вставляются в HTML через "innerHTML".
- Использование "JSON.stringify(client)" внутри встроенного обработчика события требует безопасной обработки данных.
- Поля ИНН, телефона и имени нуждаются в дополнительных ограничениях длины и формата.

"web/admin-dashboard.html":

- Данные пользователей вставляются через "innerHTML".
- Логин и роль используются при формировании встроенных обработчиков событий.
- Поля логина и пароля требуют серверной проверки длины и допустимого формата.

"web/user-dashboard.html":

- Названия и содержимое заметок, а также уведомления вставляются через "innerHTML".
- Необходимо использовать безопасный вывод динамических значений.

"web/login.html":

- Атрибут "novalidate" отключает встроенную браузерную проверку формы. Поэтому основная проверка введённых данных должна выполняться на сервере.
- CAPTCHA отображается на странице, но серверная проверка в рассмотренном обработчике отключена.
- Для изображения CAPTCHA используется англоязычный текст альтернативного описания в русскоязычном интерфейсе.

Общие замечания:

- В проверенных формах и запросах, изменяющих данные, не обнаружены явные CSRF-токены.
- В некоторых запросах необходимо дополнительно проверять "response.ok" перед обработкой ответа.
- Для динамических значений следует применять безопасные методы вывода.
- Серверная валидация должна дополнять клиентскую, а не заменяться ею.

5. Итог проверки

В ходе четвёртого этапа обнаружены проблемы разного уровня важности:

- Возможность назначения административной роли через публичную регистрацию при отсутствии дополнительной проверки полномочий.
- Использование известных значений "SECRET_KEY" и пароля БД по умолчанию.
- Потенциальные XSS-уязвимости при вставке динамических данных через "innerHTML".
- Отсутствие обнаруженной CSRF-защиты в проверенных компонентах.
- Отключённая серверная проверка CAPTCHA.
- Включённый режим отладки в "run.py".
- Ошибки HTML и JavaScript в отдельных страницах.
- Некорректная запись медиазапроса в CSS.
- Недостаточная документация проекта и отсутствие отдельных скриптов.

В первую очередь рекомендуется устранить возможность самостоятельного назначения роли администратора, убрать небезопасные значения конфигурации, реализовать CSRF-защиту и исправить небезопасную вставку динамических данных в HTML.

Проверка проводилась анализом исходного кода и структуры проекта. Полноценное динамическое тестирование всех сценариев безопасности не выполнялось.
