## 1. Публичная регистрация с возможностью назначения роли администратора

- **Файл:** `app/blueprints/auth.py`
- **Строки:** 89–90, 123
- **Категория:** контроль доступа
- **Приоритет:** высокий
- **Описание:** маршрут регистрации принимает роль пользователя из входящего JSON-запроса. При этом обязательная проверка авторизации администратора в обработчике регистрации не обнаружена.
- **Риск:** посторонний пользователь потенциально может зарегистрировать учётную запись с привилегированной ролью.
- **Рекомендация:** при публичной регистрации всегда назначать роль «Пользователь». Создание администраторов разрешать только через защищённый административный интерфейс.

## 2. Потенциальная XSS-уязвимость при динамической вставке HTML

- **Файлы:** `web/admin-dashboard.html`, `web/clients.html`, `web/materials.html`, `web/operations.html`, `web/products.html`, `web/notes.html`, `web/sales-orders.html`, `web/production-orders.html`, `web/specifications.html`, `web/user-dashboard.html`, `web/base-dashboard.html`.
- **Строки:** `admin-dashboard.html` — 20–27; `clients.html` — 24; `materials.html` — 20; `operations.html` — 20; `products.html` — 20; `notes.html` — 21–27; `sales-orders.html` — 32–37, 238–246, 303–339, 379–439, 464–529; `production-orders.html` — 47, 92, 357; `specifications.html` — 54, 82, 113–125; `user-dashboard.html` — 68, 97; `base-dashboard.html` — 442.
- **Категория:** безопасность frontend, XSS.
- **Приоритет:** высокий.
- **Описание:** обнаружены места, в которых динамические данные вставляются в HTML с помощью `innerHTML` и `insertAdjacentHTML`. Некоторые из этих данных поступают из API и могут содержать пользовательский ввод.
- **Риск:** при отсутствии корректного экранирования вредоносная разметка или JavaScript могут выполниться в браузере пользователя.
- **Рекомендация:** использовать `textContent`, безопасное создание DOM-элементов и контекстное экранирование. Проверить все места вставки динамических данных. Наличие уязвимости необходимо подтвердить отдельным безопасным тестированием.

## 3. Отсутствие обнаруженной явной CSRF-защиты

- **Файлы:** `app/__init__.py`, `app/config.py`, HTML-шаблоны в `web/`.
- **Строки:** проверены настройки приложения и шаблоны; конкретная строка отсутствует.
- **Категория:** безопасность запросов.
- **Приоритет:** средний.
- **Описание:** поиск по проекту не обнаружил `CSRFProtect`, `csrf_token`, `WTF_CSRF` и явных настроек SameSite.
- **Риск:** при отсутствии дополнительной CSRF-защиты запросы, изменяющие данные, могут быть подвержены межсайтовой подделке запросов.
- **Рекомендация:** добавить CSRF-защиту для запросов POST, PUT и DELETE, использующих авторизацию через cookie. Проверить настройки cookie и поведение браузеров.

## 4. Небезопасное значение SECRET_KEY по умолчанию

- **Файл:** `app/config.py`
- **Строка:** 59
- **Категория:** управление секретами.
- **Приоритет:** высокий.
- **Описание:** если переменная окружения `SECRET_KEY` отсутствует, используется заранее заданное значение `production-is-system-secret-key-change-me`.
- **Риск:** использование известного секретного ключа может поставить под угрозу безопасность сессий и подписанных данных.
- **Рекомендация:** не допускать запуск production-конфигурации с ключом по умолчанию. Требовать уникальный случайный секрет из переменных окружения.

## 5. Слабый пароль базы данных по умолчанию

- **Строки:** 53–54

## 7. Отсутствие явных настроек безопасности cookie

- **Файл:** `app/config.py`
- **Строки:** 59–61
- **Категория:** безопасность сессий.
- **Приоритет:** низкий.
- **Описание:** явные настройки `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_HTTPONLY` и `SESSION_COOKIE_SAMESITE` не обнаружены.
- **Риск:** отсутствие явной настройки затрудняет контроль безопасности сессий в production.
- **Рекомендация:** для production использовать HTTPS и установить `SESSION_COOKIE_SECURE = True`, `SESSION_COOKIE_HTTPONLY = True`, а также подходящее значение `SESSION_COOKIE_SAMESITE`, например `Lax`.
